# Google Play: the Android app on the store and its subscriptions

Mam-IA for Android (`app.mamia.android`) can be installed in two ways:

- **Direct download**: the APK served by the server itself at `/android.apk`. The landing page shows the button when
  `/api/android` says `available: true`.
- **Google Play**: the store. Inside the app, the family subscription is bought with Google Play, because Play does
  not allow charging for digital subscriptions any other way. On the web, payment is still done with Stripe.

With the key generated by Google, the Play version and the server's APK have different signatures: each one updates
over itself, not over the other. This guide follows what already works in BodyLens.

## 1. The signing key (once, you create it)

```bash
cd ~/PycharmProjects/Mam-IA && tools/android-keystore.sh
```

- It creates `~/mamia-upload.jks`, with the password you choose.
- It stores the key in 4 repository secrets: `ANDROID_KEYSTORE_B64`, `ANDROID_KEYSTORE_PASSWORD`,
  `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD`.
- **Keep the `.jks` and its password in your password manager.** If they are lost, no new version can be installed
  over the previous ones.

Without those secrets, GitHub signs each build with a new debug key. The signature changes with every version and an
APK cannot be installed over the previous one. The GitHub Actions log tells you which one was used: the
«Android signature» note says `release key` or `DEBUG key`, together with the SHA-256 fingerprint. The fingerprint can
also be seen like this:

```bash
apksigner verify --print-certs mamia-android.apk
```

(`apksigner` comes with the Android SDK build-tools; `keytool -printcert -jarfile` does not see the v2 signature of
modern APKs.)

## 2. Build and publish the APK

- Every change in `android/` builds the APK and the AAB and leaves them in the `android-latest` pre-release on GitHub
  (`.github/workflows/android.yml`). The AAB is the file that is uploaded to Play.
- To take the APK to the server:

  ```bash
  tools/deploy-android.sh
  ```

  It copies it to `<DATA_DIR>/android/` on the NAS. Then check that `https://mamia.jtgcloud.com/api/android` says
  `"available": true` and that `/android.apk` downloads.
- The icon is the brand one: `tools/make_icons.py` generates both `assets/branding/` and the Android icon.

## 3. Play Console: create the app

- Name: **Mam-IA**. Default language: **English (en-US)**, as in BodyLens; Spanish goes as a translation. Add store
  listing translations if you want (the app is in 10 languages).
- App, **free**: the subscriptions are in-app products.
- Category: **Productividad** or **Crianza** (Parenting).
- Contact: `mamia@jtgcloud.com`, website `https://mamia.jtgcloud.com`.
- Store listing icon: `assets/branding/icon-maskable-512.png` (512×512, full square: Play rounds the corners).
- Store listing images, in the 10 languages: `assets/play-store/<Play code>/` (`es-ES`, `en-US`, `ca`, `fr-FR`,
  `it-IT`, `de-DE`, `pt-PT`, `nl-NL`, `zh-CN`, `ja-JP`), with `feature-graphic.png` (1024×500), `phone/` (1080×1920),
  `tablet/` (1440×2560, the same for 7" and 10") and `chromebook/` (2880×1620), and the store listing texts in that
  language (`title.txt`, `short_description.txt`, `full_description.txt`). Google Play shows each visitor the store
  listing translation in their language, with its screenshots; if their language has no translation, it shows the
  default one (en-US). They are made by `tools/play_screenshots.py` with the real app and the sample family from
  `app.demo.play_review`, with the interface and the family's texts in each language. The «📸 Google Play images»
  workflow regenerates them and pushes them to the same branch (`main` or the release branch, `X.Y.Z`) every time the
  interface, the translations or the sample family change. On a release branch, it also uploads them to Google Play
  (section 9).
- App signing: **key generated by Google** (Play App Signing), as in BodyLens. `mamia-upload.jks` is only the upload
  key. That is why the Play app and the server's APK have different signatures: whoever has one installed has to
  uninstall it to switch to the other.
- **Automatic protection**: turned off, because the direct APK is also distributed.
- Play requirements for the AAB: Play Billing 8.0.0 or newer and target SDK 36 (already in `android/`).
- Android developer verification: register the package `app.mamia.android`.

## 4. The subscription

In **Monetizar → Productos → Suscripciones**, create the subscription with ID **`mamia`**:

| Base plan | Renewal | Price | Offer |
|---|---|---|---|
| `monthly` | Monthly | €2.50 | 7-day free trial (for new customers) |
| `yearly` | Yearly | €25 | 7-day free trial (for new customers) |

The IDs have to be exactly those: the app requests the product `mamia` and its plans `monthly` and `yearly`. One
subscription covers the whole family.

## 5. The service account (so the server can verify purchases)

1. In Google Cloud, in the project linked to the Play Console: **IAM → Cuentas de servicio → Crear**. Then,
   **Claves → Añadir clave → JSON** and download the file.
2. In Play Console: **Gestionar cuenta → Usuarios y permisos → Invitar a nuevos usuarios**, with the service
   account's email (`…@….iam.gserviceaccount.com`). The permissions it needs, also for the automatic upload, are in
   section 9.
3. In Mam-IA, go to **Administration → Business → Google Play** and fill in:
   - Package: `app.mamia.android`.
   - Subscription: `mamia`.
   - Paste the **contents** of the JSON.

   Save. The key is stored encrypted and is never shown again: only its `client_email` is visible.
4. Once the app is published, also put the store listing link there
   (`https://play.google.com/store/apps/details?id=app.mamia.android`). The landing page will show the Google Play
   button.
5. For **Business** to show Google Play installs and revenue, also set the reports URI. In Play Console:
   **Gestionar cuenta → Informes de aplicaciones de Play**, choose **Estadísticas** and click **Copiar URI de Cloud
   Storage** (it starts with `pubsite_prod_rev_`). Paste it into «Cloud Storage URI of the reports» and click «Test
   the reports». The service account needs, in Usuarios y permisos, **Ver información de la aplicación** and **Ver
   datos financieros** for the whole account (not just for Mam-IA). Google publishes the statistics a few days late,
   and each month's revenue report around the 5th of the following month.

While there is no service account, the app does not offer paying with Google Play: you get in with a code, by
invitation, or with a web subscription.

## 6. App content (Política → Contenido de la app)

| Section (as in Play Console) | Answer |
|---|---|
| Política de privacidad (Privacy policy) | `https://mamia.jtgcloud.com/privacidad` |
| Anuncios (Ads) | **No** |
| Acceso a la app (App access) | Restricted. Give the email and password of a **test account with made-up data**, never your own. |
| Público objetivo (Target audience) | **18 years or older**: it is created and used by adults; the kids are profiles without an account. |
| Funciones financieras (Financial features) | None |
| Eliminación de la cuenta (Account deletion) | In the app (Your account → Delete my account) and on the web: `https://mamia.jtgcloud.com/borrar-cuenta` |
| Alarmas exactas (`SCHEDULE_EXACT_ALARM`) | Declare that it is a **calendar and reminders** app: it notifies of plans and tasks at their time. |

**Clasificación de contenido (IARC)** (Content rating): all the questions, **No**. Users interact: **Yes**, only inside the family (they share the
agenda, tasks and shopping list). Digital purchases: **Yes** (subscriptions).

**Seguridad de los datos** (Data safety):

- Data collected (all of it: collected yes, shared no):
  - name and email (required, for the account);
  - the family data the user enters (calendar, tasks, notes; optional, for the app to work);
  - the kids' health notes (allergies, vaccines; optional);
  - purchase history (the subscription status).
- Encrypted in transit: **Yes**.
- Can be deleted: **Yes**.
- Location, contacts, photos and advertising identifiers are not collected.

## 7. The reviewers' account (Acceso a la app)

Mam-IA can only be used when signed in, so Google asks for test credentials. A dedicated account is used for the
reviewers, with a sample family: a couple, two kids with their profile, an agenda for this week and the next, tasks
and routines, the shopping list and the menu. Everything is made up.

Create and fill it on the NAS. The script asks for the password the first time and neither shows nor stores it:

```bash
ssh nas
```

```bash
sudo docker exec -it mamia python -m app.demo.play_review playreview@jtgcloud.com
```

Or without typing the password yourself: a random one is generated and saved only in a file on the NAS (it is not
shown):

```bash
sudo docker exec mamia python -m app.demo.play_review playreview@jtgcloud.com --password-file /data/secrets/playreview.txt
```

```bash
sudo cat /volume1/docker/data/mamia/secrets/playreview.txt
```

- It can be run again whenever you want: it rewrites the same data with dates around today (the agenda stays current)
  and duplicates nothing.
- The family is free forever, it never becomes read-only.
- The couple (`sam@demo.mamia.invalid`) is a demo account, without a password: nobody can sign in with it.

In Play Console → Contenido de la app → **Acceso a la app**: «Todas o algunas funciones están restringidas» → add
the email `playreview@jtgcloud.com`, the password you chose and these instructions:

```
Sign in with the email and password above (server: https://mamia.jtgcloud.com).
The account belongs to a sample family with made-up data: agenda, tasks, shopping list, weekly menu and kids' info.
```

## 8. Before the first upload

- Create the key (step 1) and wait for GitHub to build with it: the Actions log must say `release key`.
- Upload `mamia-android.aab` (from the `android-latest` release) to an internal test, set up the subscription and the
  service account, and test a purchase with a license-testing account (Configuración → Pruebas de licencia).

## 9. Automatic upload to Google Play

On every release branch (`X.Y.Z`), GitHub uploads to Google Play by itself:

- **The app**: every AAB build (`.github/workflows/android.yml`) goes to the track in the `PLAY_TRACK` variable,
  `alpha` by default, the closed test, with its release notes (section 10). A new release always builds and uploads,
  because `tools/CreateUpdateRelease.py` changes the version in `android/app/build.gradle.kts`. Web-only changes do
  not need a new app version: the app loads the server's web.
- **The store listing**: the texts and images in `assets/play-store/` in the 10 languages («📸 Google Play images»).
  Only the images that changed are uploaded again. The Chromebook screenshots are not in the API: they are uploaded by
  hand.

**The version is the same everywhere.** `versionName` is the release version (`0.2.0`), the same as the repository's,
the CHANGELOG's and the server's. `versionCode` is the GitHub build number, which Play requires to go up on every
upload. In Play Console it shows as `0.2.0 (45)`. If the Gradle version does not match the branch, the upload fails.

`tools/play_publish.py` does it, with the Google Play API. Google still reviews every version and every store listing
change. Mam-IA, BodyLens and MeetGo upload the same way: same default track, same version name and same notices. When
the version reaches `main`, it is published by itself: GitHub release and, with production access, Play (section 10).

**Setup (once):**

1. **Play Console → Gestionar cuenta → Usuarios y permisos → Invitar a nuevos usuarios**: the email of the service
   account from section 5, with no expiry date. In the **Permisos de la cuenta** tab (they apply to all apps), tick
   «Ver información de las aplicaciones y descargar informes en bloque (solo lectura)», «Ver datos financieros,
   pedidos y respuestas a encuestas de cancelación», «Gestionar pedidos y suscripciones», «Lanzar aplicaciones en
   canales de pruebas», «Lanzar a producción, excluir dispositivos y usar la firma de aplicaciones de Play» and
   «Gestionar la presencia en Play Store». **Invitar usuario**. If it was already invited, open it with **Gestionar**
   on its row and tick whatever is missing.
2. **Google Cloud** (that account's project): **APIs y servicios → Biblioteca**, search for «Google Play Android
   Developer API» and click **Habilitar** (if it is already enabled, there is nothing to do).
3. **GitHub → jaimetur/Mam-IA → Settings → Secrets and variables → Actions**:
   - **Secrets → New repository secret** tab: name `PLAY_SERVICE_ACCOUNT_JSON`, value: the whole contents of the
     service account's JSON (or, from the repository folder, `gh secret set PLAY_SERVICE_ACCOUNT_JSON <
     ruta/clave.json`);
   - **Variables → New repository variable** tab (optional): `PLAY_TRACK`, the track for the `X.Y.Z` branches,
     `alpha` by default: the track Play creates for the closed test («Alpha» in **Probar y publicar → Pruebas →
     Prueba cerrada**). If your closed test is a track you created yourself, put its name here. The stable track
     (`PLAY_STABLE_TRACK`) is a different one: section 10.
4. Test: **Actions → 🤖 Android app → Run workflow**, branch `0.2.0`. The log must end with
   «0.2.0 (N) uploaded to the alpha track», and the new version appears in Play Console → Prueba cerrada.

Without the secret, the workflows keep working and warn that they have not uploaded anything to Google Play.

## 10. Final release, release notes and production

When a version reaches `main` (when its `X.Y.Z` branch is merged), «🚀 Release» (`.github/workflows/release.yml`)
publishes it by itself:

- **GitHub**: the `vX.Y.Z` release, marked as the latest, with the notes from that version's block in `CHANGELOG.md`,
  the source code and the app's APK and AAB. If the version already had a release, it is published again on the new
  commit.
- **Google Play**: the build of that version that the testers have in the closed test is promoted to the stable track
  in the `PLAY_STABLE_TRACK` variable (`production`), with its notes. It is the same build they tested: it is not
  built again. If the closed test does not have that version, it fails and says so: run the Android workflow on the
  branch first. While `PLAY_STABLE_TRACK` does not exist, the GitHub release is published anyway and the version
  stays in the closed test.

**Release notes.** They come from the version's block in `CHANGELOG.md`, for GitHub and for Play («Novedades», on each
upload to the closed test and when promoting to production):

- GitHub gets the whole block.
- Play allows at most 500 characters per language. If the block has `#### 📱 Google Play (<language>):` sections, one
  per language, their text is sent as is. If not, the titles of its new features, improvements and fixes are sent, in
  Spanish. Only the languages the store listing has are sent, and the 📱 sections do not appear on GitHub.

```markdown
#### 📱 Google Play (es-ES):
Nuevo diseño pensado para el móvil, agenda familiar y lista de la compra en directo.

#### 📱 Google Play (en-US):
A new phone-first design, a family calendar and a live shopping list.
```

To see what Play would receive: `python tools/play_publish.py --promote --version 0.2.0 --dry-run`.

**Going to production (once).** With a personal developer account, Google first requires a closed test with at least
12 testers for 14 consecutive days. Then, in Play Console → **Panel → Solicitar acceso a producción**. Once Google
grants it:

1. The service account needs «Lanzar a producción, excluir dispositivos y usar la firma de aplicaciones de Play». If
   you invited it as in section 9, it already has it. If not: **Gestionar cuenta → Usuarios y permisos →
   Gestionar** on its row, and tick it.
2. **Play Console → Probar y publicar → Producción → pestaña Países o territorios → Añadir países o territorios**:
   add the countries where it is published and save the changes. Without countries, the upload to production fails.
3. Enable the stable track (in the terminal, from any folder):

   ```bash
   gh variable set PLAY_STABLE_TRACK --body production -R jaimetur/Mam-IA
   ```

   The 3 apps (Mam-IA, BodyLens and MeetGo) at once:

   ```bash
   for r in Mam-IA BodyLens MeetGo; do gh variable set PLAY_STABLE_TRACK --body production -R jaimetur/$r; done
   ```

4. Test: **Actions → 🚀 Release → Run workflow**, branch `main`. The log must end with
   «X.Y.Z sent to the production track».

From then on, the `X.Y.Z` branches keep uploading to the closed test and what reaches `main` goes to production, for
all users as soon as Google approves it. There is no staged rollout (percentage of users): with few users it adds
nothing, and the percentage would have to be raised by hand in Play Console.
